## 开篇

> **一个遥控器，加一个哨兵。**
> 当你不在跑着 Kimi Code 的那台机器面前时，你仍能**指挥**它，它也会在需要你时**主动穿过锁屏**找到你。

它不是"又一个 Kimi 客户端"。它的存在，建立在**"人机分离是常态"**这一事实上——而 Kimi 默认假设你在场。这个错位，就是整个产品的全部空间。

# 定义

## §01 定位 · 它是什么 / 不是什么

> 这张表是本卷的**灵魂**。后续任何设计若让产品滑向右列，即偏离定义，应被否决。

| 它是                                                | 它不是                                       |
| --------------------------------------------------- | -------------------------------------------- |
| **遥控 + 哨兵**：不在场也能指挥、也能被叫醒         | 移动版终端：把黑底白字塞进手机，那只是缩小   |
| 会话是**活的**：打开即见 agent 此刻在想、在跑、在等 | 会话**列表**：点进去才看得见——待办软件的气质 |
| **许可**是一等公民：危险动作变成可秒判的请求        | 日志查看器：只让看、不让拦，事后尸检         |
| 数据在**自己机器**上：自托管，不经第三方云          | 云服务：要注册、要上传代码上下文             |
| 为**一个人伺候自己**而锋利                          | 为"吸引 star"而通用                          |

## §02 背景与动机

**真实的痛（自用）**：在电脑前起一个长任务后离开（合盖、出门、骑车、做饭），于是陷入三难——**够不着键盘**时想插话改方向做不到；**不知道它卡在哪**时，一个两分钟能拍板的危险操作把任务吊死几十分钟；**不知道它跑没跑完**时，要么反复回去看、要么忘了它。这三件事，现有所有形态都解决不了——因为它们都假设你**坐在那台机器前**。

**现有方案与结构性缺口（诚实陈述）**：

| 方案                           | 给了什么                                | 结构性缺口                                                   |
| ------------------------------ | --------------------------------------- | ------------------------------------------------------------ |
| Kimi 原生终端 TUI              | 电脑前体验最好                          | 假设你在场，离开即失联                                       |
| 官方 `kimi web`                | 本机网页服务                            | 本地网页非多端产品；移动是凑合网页、无推送、无后台、合盖即没 |
| kimi-gui（个人，Electron）     | 完整桌面 GUI，迭代极快                  | 纯桌面，无移动端                                             |
| Paseo（官方推荐多端编排器）    | 桌面/网页/移动多端                      | 多端已做，但移动端是否原生、推送与同步是否到位待考；是"够不够好"而非"有没有" |
| 官方 **#2269** feature request | "Remote Control / Multi-Device Session" | **正是本产品要做的事，官方列为 feature request、未实现**     |

> **结论**：赛道被反复验证为真，官方未做，第三方各做一角。本产品不靠"没人做"立足，而靠**"把不在场这件事做到位"**立足。

## §03 目标用户与使用语境

- **v1 目标用户 = 作者本人**，单人、自托管、不共享。
- 使用语境核心是**人机分离**：人 ≠ 跑 agent 的机器，且分离是常态而非例外。
- 由此推出 v1 一切取舍：**不为多人设计**（无账号、无团队、无权限），**数据不离开自己的机器**（自托管中继，不上云同步代码上下文）。

## §04 核心问题 · 三大价值支柱

> 如何让一个"默认需要人在场"的 agent，在人不在场时，依然可被指挥、可被监督、可在关键时刻取得人的许可——并让人始终知道它和机器此刻是什么状态？

拆为三个子问题，对应三大支柱；另有一个支撑性能力「机器体检」收进第三支柱的"可见"维度。

**支柱 01 · 遥控（你主动伸手）**
不在场时仍能发指令、能**叫停**跑飞的方向、能中途改航向。形态可多样（文字、未来语音），本质是"你的意图能实时抵达那台机器并被执行"。

**支柱 02 · 哨兵（它主动找你）**
agent 不该在需要你时傻等，也不该擅自做危险决定。三类时刻**主动穿过锁屏**：① 需要你**许可**一个拿不准的动作；② 一轮**跑完**（成败都给值得看的结果）；③ 机器**将睡或断线**。分寸：**叫你拍板，但不替你自动驾驶**；默认保守，油门由你给。

**支柱 03 · 连续 · 诚实 · 可见（含机器体检）**
**连续**——合上电脑、换个屏幕，看到的还是同一条活会话的当下，而非尸体或另一份副本。**诚实**——机器睡了、通道断了，立刻、显眼地告诉你，绝不让你对着空气发指令。**可见**——人不在场也能远程掌握机器的配置与健康（模型 / MCP 连接 / skills / 权限），即「机器体检」，是遥控与哨兵之外的第三件事。

## §05 产品原则

> "产品选择以何种方式存在"的根本决定，不依赖技术事实；技术实现归设计层。

1. **单一真相，多端一致**：无论手机还是桌面，看到的是同一份真相——同一条流、同一张待许可请求、同一个"已许可"事实。任何屏幕只是这份真相的视图。此原则是"会话漂移"成立的前提。
2. **数据在你机器上**：自托管，会话与代码上下文不经第三方云。
3. **为一人锋利**：v1 每个决定都问"这让我自己用着更爽吗"，不问"这能让别人喜欢吗"。
4. **诚实优于假装**：状态、连通、保活能力，宁可说"我做不到 / 我断了"，也不装作正常。
5. **形态决定气质**：主交互必须是"盯一条活的流、在它需要时拍一下板"，而非"浏览清单、点进去填表"——后者会让产品坍缩成待办 / 记账那一族。
6. **默认保守** ✅ *v0 实测焊死*：Kimi 的许可经 ACP `request_permission` 同步阻塞，未获批准前工具不执行；实测 reject 后 agent 不重试、不绕过。据此守住"默认保守"：**超时未选择默认拒绝**（中继在 ACP client 层裁决）；fail-open 仅在启用 hook 兜底路时需额外防范。
7. **封装不越界**：复用 Kimi 原生能力（含配置命令），不另起炉灶重造 agent 或重造配置编辑器。

## §06 地基假设 / Kill Switch ✅

> **假设**：Kimi 允许外部程序拦截并许可 / 否决其工具调用。

- **实测（2026-07-31，Kimi Code CLI 0.31.0）**：default 模式下，工具执行前发 `session/request_permission`；client 回 `reject`（reject_once）后，`tool_call` status 变 `failed`，命令**未执行**。
- **结论**：拦截可编程、reject 真阻断。**路 B（ACP）确认主路。**
- **附加发现**：reject 后 agent 不重试、不绕过，并向用户说明"被拒绝"——许可语义被 agent 尊重，这让"拒绝"不是被无视的。
- **fail-open 注**：ACP `request_permission` 为同步阻塞，"未批准不执行"由协议保证；fail-open 仅为 hook 兜底路（路 A）的注意事项，**ACP 路没有 600s 上限**，超时时长完全自由。

# 设计

## §08 系统架构

**拓扑**：

```
┌──────────────── 那台跑 Kimi 的机器（电脑）────────────────┐
│  ┌──────────┐ stdio(ACP) ┌───────────────────────────┐  │
│  │ kimi acp │◄──────────►│     中继 (Go, 常驻)        │  │
│  │ (子进程)  │            │ ① ACP client              │  │
│  └──────────            │ ② 会话状态机 sid→state     │  │
│   ▲ 复用登录态            │ ③ 许可裁决器 per-session   │  │
│   │ KIMI_CODE_HOME       │ ④ 多端广播器 ⑤ 状态持久化  │  │
│                          │ ⑥ 心跳 / 在线检测           │  │
│                          └─────────────┬─────────────┘  │
└──────────────────────────────────────────┼───────────────┘
                                           │ 对外端点 [可插拔]
                                           ▼  Tailscale / 本地 WS
                                ┌─────────────────────┐
                                │ 手机 (Flutter) 纯视图 │  + Bark 门铃
                                └─────────────────────┘
```

**三条铁律**：

- **中继是唯一持状态者**。会话跑到哪、哪张卡待批准、谁批准了——权威副本全在中继的 `sid → state` map 里。手机与桌面**只是视图**，发的是**意图**（批准 / 发指令 / 中断 / 切 mode），中继改 map 后广播。这是原则 1「单一真相」的物理落地，也是 v2 桌面端"零改造接回同一条流"的前提。
- **中继 ↔ Kimi 走 stdio**（ACP 规定，newline-delimited JSON-RPC，v0 已证实）。
- **中继 ↔ 端走 WebSocket**（双向实时：流往下推、批准 / 指令往上回；不用 SSE，因其单向）。

**中继六职责（产品的真正内核，UI 只是它的皮）**：

| 职责          | 干什么                                                       |
| ------------- | ------------------------------------------------------------ |
| ① ACP client  | spawn 并持有 kimi acp；发 initialize / session/new / prompt / cancel / set_mode；收 session/update 流；**应答 request_permission** |
| ② 会话状态机  | 每个 sid 一份 state：当前 mode、流缓冲、工具调用生命周期、**待批准 permission 队列**、最后活跃时间。会话状态机除待批准队列外，还需处理一种 update 类型 config_option_update（旁路更新该 sid 的配置快照，供新连接补发）。 |
| ③ 许可裁决器  | 收到 permission → 查该 sid 的 mode 策略 → manual：转端等回应 + **超时默认拒绝**；yolo/auto：自动回 allow_once；plan：不应有工具调用，出现即记异常 |
| ④ 多端广播器  | state 变化 → 推给所有连着的端（v1 只有手机，但按多端写）     |
| ⑤ 状态持久化  | state 落盘，中继重启 / 端重连能续上，不丢"它正等你批准"      |
| ⑥ 心跳 / 在线 | 检测 kimi 进程活没活、电脑睡没睡 → 维护三态。kimi 子进程退出由 generation 计数判定"非预期"，触发广播 relay.state=degraded + permission.invalidate；上行 restart_kimi 触发 Restart + initialize + 逐 sid session/resume{sessionId,cwd} |

**两条核心数据流**：

> **流 A · 哨兵批准（命脉）**
> kimi 想跑命令 ──`request_permission(sid,tool,options)`──► 中继查 sid.mode：**manual** → 写"待批准卡"进 state、广播给端（+Bark 门铃），等端回应或**超时自动回 reject_once**；**yolo/auto** → 直接回 allow_once。中继 ──response──► kimi ──► 执行 or failed ──`tool_call_update`──► 中继广播。

> **流 B · 遥控**
> 端输入框 ──意图(prompt)──► 中继 ──`session/prompt(sid,text)`──► kimi；kimi ──`session/update(thought/message/tool_call…)`──► 中继广播。端点「停」──意图(cancel)──► 中继 ──`session/cancel(sid)`──► kimi。

**对外通道** ✅ *定稿*：

- **数据通道**：Tailscale 虚拟 IP 上的 WebSocket，跨网络可用，内容点对点加密，契合原则 2。中继内部广播器不感知差异（本地 WS / 公网隧道只是两种接入）。
- **锁屏叫醒（v1）**：Bark 免费门铃——中继调其 API 弹通知，免费、立刻可用、覆盖骑车锁屏。通知**只当门铃、不传会话内容**。
- **锁屏完美闭环（v2 按需）**：APNs，点通知直达 App 内批准卡，需 $99，等愿意为闭环付费时再做。

> **为什么 Bark 而非 ngrok 直接搞定锁屏**
> ngrok / Tailscale 穿的是"端主动连中继"的连接，连接靠 App 进程维持；iOS 锁屏久了会**杀掉后台 App 进程**，连接随之断，没有活进程去弹窗。APNs / Bark 走系统级推送，**弹窗由 iOS 系统进程执行**（系统进程不死），故能在 App 被杀时叫醒。所以"数据通道"与"锁屏叫醒"是两件独立的事，分开定。

**登录与部署**：

- **登录**：中继 spawn kimi acp 时复用 `KIMI_CODE_HOME` 的 device-code 登录态（一次性，人 + 浏览器 + 终端）。**手机端永不碰登录**。
- **部署**：中继 = 电脑上的**常驻守护进程**（开机自启 / 崩溃自重启 kimi acp）。它挂 = 任务断，故自启与"崩溃后诚实告知端"是 v1 必做。

## §09 主屏形态（防坍缩的第一刀）

> 这一章回答的不是"有哪些按钮"，是"打开 App 第一眼，它的气质像什么"。原则 5 立了"形态决定气质"，这里落地。

**第一眼：一条活的流，不是一个列表**

打开 App，**主屏 = 此刻正在跑的那条会话的实时流**，像看一场直播。不是"会话列表，点进去才看得见"——那是待办软件的气质，会让产品坍缩。**列表退到配角**。只有没有任何活跃会话时，主屏才退成空态。

**这条流由什么组成（映射 v0 实测 update 类型）**：

| 流里的块   | 来自                  | 在主屏的样子                                                 |
| ---------- | --------------------- | ------------------------------------------------------------ |
| 思考区     | `agent_thought_chunk` | 默认**折叠成一行**"正在思考…"，点开才看全文                  |
| 回复区     | `agent_message_chunk` | **主体**，逐字流式往下吐                                     |
| 工具调用卡 | `tool_call` 生命周期  | pending→流式拼命令→**等批准时就地变批准卡**→completed 折叠 / failed 红字 |
| 批准卡     | `request_permission`  | **浮在这条流的当下位置**，不是二级页、不是弹窗               |

**顶栏：永远回答"我在遥控谁、它醒没醒、谁在等我"**

常驻三样：① **在线三态灯**；② **当前机器名**（多端产品的"我遥控的是谁"必须永远可见，复用为机器体检入口）；③ **会话切换器 + 待批准角标**。

> 批准卡不是独立组件，它是工具调用卡在"等批准"状态下的形态。这让"许可是一等公民"在视觉上成立——你不是去某个菜单里找批准，你是盯着流，流停在哪张卡，哪张卡就在问你。

**防坍缩论证**：主交互 = **盯一条活的流 + 在它需要时拍一下板**。不是"浏览清单"（待办 / 记账），不是"点进去填表"（管理后台），批准不是"去某个页面操作"。三条守住，产品就从根上离开了记账 / 待办那一族。**任何后续设计若把主屏改回"列表为主"，即违背原则 5，应被否决。**

## §10 哨兵 · 批准卡精确规格

> 把"批准"这一个动作拆到状态机的每一帧——哨兵能不能让人 trust，全看这几帧顺不顺。
> *（可亲手感受状态转换的活 demo 见 `sentinel-prototype.html` 与 `sentinel-design-spec.html` §10。）*

**3.0 脊柱：批准卡是一个状态机**

| 状态       | 触发（v0 事件）                    | 卡的样子                                           | 此刻能做什么                |
| ---------- | ---------------------------------- | -------------------------------------------------- | --------------------------- |
| S0 预告    | tool_call(pending) + 流式 update   | "正在拼命令"，**还没按钮**                         | 只能看                      |
| S1 待批准  | request_permission 到达            | 命令定格，**三出口亮起**，倒计时开始，风险色上边框 | 批准 / 本会话 / 拒绝 / 展开 |
| S2a 执行中 | 点 approve_*                       | 按钮收掉，spinner + "执行中…"                      | 等，或点「停」              |
| S2b 已拒绝 | 点 reject 或超时                   | 红字"已拒绝"                                       | 无（成历史）                |
| S3 结果    | tool_call_update(completed/failed) | 折叠一行：绿✓ / 红✗                                | 点开看完整输出              |

S0→S1 之间用户**不能**提前批准——Kimi 还没发 permission，提前点没东西可批。按钮只在 S1 出现，是纪律。

**3.1 信息架构：S1 一眼能判（锁屏 2 秒法则）**

四行，不多不少：① 动作类型 + 风险色（上边框颜色，比读字快）；② 命令原文（等宽，单行截断，全文靠展开）；③ 它的一句理由（取 toolCall.content，**agent 解释自己**）；④ 三出口 + 展开 + 倒计时。少一行判不了，多一行扫不完。

**3.2 三出口：对齐 Kimi 原生结构**

| 按钮           | optionId         | 文案（诚实优先）                                             |
| -------------- | ---------------- | ------------------------------------------------------------ |
| 批准这次       | `approve_once`   | "批准"                                                       |
| 本会话同类批准 | `approve_always` | "本会话都批准"（沿用 Kimi 原生 "Approve for this session"，**绝不写成"永久记住"**） |
| 拒绝           | `reject`         | "拒绝"                                                       |

三按钮**平铺**，语义 / 顺序对齐 Kimi 原生 options，不自创第四种交互、不做主次翻转。

**3.3 无损展开：敢不敢点，取决于能不能先看**

展开箭头点开后命令全文 / diff 在卡内撑开，三出口**原地不动、不消失、不触发任何 outcome**。若展开 = 批准，用户就永远不敢展开，哨兵退化成猜谜。**展开必须是一次免费的窥探。**

**3.4 二元风险：中继启发式判，无白名单**

| 关键命令 🔴                        | 非关键 🟢                     |
| --------------------------------- | ---------------------------- |
| `rm -rf build/ && npm run deploy` | `cat coverage.txt`           |
| 命中内置关键清单，要你确认        | 未命中清单，中性，扫一眼即批 |

> **诚实声明**：v0 实测 permission 参数**无显式 risk level**，风险色是中继启发式判的，非 Kimi 原生。v1 内置一份**短的关键命令清单**（rm -rf / sudo / git push -f / git reset --hard / 写凭证文件 / curl\|sh / deploy / 删库），命中 = 红、要你确认；其余中性。**不维护白名单**——维护痛 ＞ 误判痛。认知从"三档"降到"红 / 不红"，更符合锁屏 2 秒法则。机器体检里只读展示这份清单，让哨兵标红时用户看得见"凭啥这条红"。

**3.5 超时：一律拒绝 + 一个可选开关**

**超时一律拒绝**（一句话规则）。外加**一个**可选全局开关「非关键命令超时自动放行」，**默认关**。开关关 = 夜里全拒、早上看一堆"已超时拒绝"门铃（保守一致零维护）；开关开 = 夜里非关键自动过、只把关键留到早上。无论哪种，**Bark 补一条门铃**，让超时不是悄悄发生。ACP 路无 Kimi 侧超时，时长完全自由。

**3.6 批量聚合** 🔴 *待验*

同一会话 1.5s 窗口内多个待批准聚成一张"批卡"，逐条独立勾，**震一下**。但每条决定独立，**绝不合成模糊的"批准全部"**（踩串味坑）。v0 只测单条，单会话并行 permission 是否真发生待开发观察；若 Kimi 单会话串行调工具，则退化为逐张卡，此设计备而不用。

**3.7 门铃 → 落卡：Bark 摩擦靠"自动落卡"补回**

点 Bark 通知打开的是 Bark 不是 App（v1 接受这一下摩擦）。切回 App 时**自动落卡**：连中继 → 问"最新待批准是哪个 sid 的哪张卡" → **先切 sid，再滚到该卡，再高亮闪一下**。顺序不能反（反了滚到错误的流）。损失只是"点一下直接进 App"那一下，没损失"找卡"的脑力。v2 上 APNs 补回完美闭环。

## §11 多会话交互

> 多会话不是"加一个列表"，是把批准卡的每个交互**乘上 sid 维度**再走一遍，确保不串味。

**切换器：单会话退场，多会话现身**

单会话时标签列**退场**（安静，不暗示"该切换"）；第二个会话建起才淡入。每标签 = 会话名 + **状态点**（🟢在跑 / 🟠等你批准）+ C 位高亮条。状态点是**会话级**，与机器级三态灯正交——机器⚫时所有会话点带斜杠，因为谁也跑不动。

**切走 ≠ 暂停**

> **焊死**：切到别的会话只是"主屏不显示它"，**不是暂停它**。后台会话的流照进中继 state、照弹 permission、照跑完。若开发把"切走"实现成"暂停 update 处理"，一票否决——那会制造"我以为它停了结果它偷偷跑完 / 卡住"的灾难。

**后台弹 permission 的三处协同（盯着 C 位也不漏后台）**

后台会话的批准卡**不会出现在 C 位流里**（防串味）——App 收到了，但故意改用三处不污染 C 位流的方式提醒：① 切换器该标签变🟠； 待批准角标 +1；③ Bark 门铃带 sid 名。三处用同一份事实，恒一致。**角标 = 🟠标签数 = 有待批准的会话数**，恒等。

> **两种"后台"别混**：会话后台（App 在前台活着）能弹窗，只是故意不弹错地方；进程后台（App 被 iOS 杀）才纯靠 Bark 门铃叫醒。详见 §08 对外通道说明。

**待批准队列：多会话下最值钱的视图**

角标点开 = 全屏"所有等你批准的卡"列表，**按 sid 分组**，每组标题可点切 C 位，每条点一下 = 切 sid 并落该卡。让你不用逐个会话翻就知道谁卡住、卡在哪。单会话时退化成空 / 单组、零负担——故**进 v1**，不做它多会话就是负担不是能力。

**会话较多时的展示（4.10）**

- **顶栏标签区**：只显示 C 位 + 所有🟠 + 最近 2 个活跃，横滑；其余折叠。保证"最该看见的"永远在眼前。
- **「全部会话」总览**：标签区末尾 ⋯ / 全部 入口，点开列表——每行 = 名 + 状态点 + 最后活跃 + 当前 mode + 待批准数；支持搜索 / 按状态筛选（全部 / 等批准 / 在跑 / 完成）。
- **分工**：全部会话 = 导航所有会话；待批准队列 = 处理卡住的会话。一个找路，一个救火，不重叠。
- v1 范围：横滑 + 全部会话列表（基础版）；搜索 / 筛选标 ⏳ *v1.5*。

**防串味自检（七处必带 sid，漏一处即 bug）**

| 位置                        | 串味后果                 |
| --------------------------- | ------------------------ |
| 门铃文案（第一字段）        | 锁屏分不清哪个任务       |
| 切换器状态点🟠               | 不知道谁卡住             |
| 待批准角标                  | 数字和标签对不上         |
| 待批准队列分组              | 卡张冠李戴               |
| 落卡（先切 sid 再滚卡）     | 落到错误的流             |
| 流里的批准卡                | 在 A 的流里批了 B 的命令 |
| 遥控输入框（发给 C 位 sid） | 想指挥 A 结果发给了 B    |

## §12 在线 · 诚实 · 连续

> 这章只守一件事——**灯说的，必须是真的**。

**三态精确判定（含校准）**

| 灯   | 精确判定                                             | 此刻能做什么                                          |
| ---- | ---------------------------------------------------- | ----------------------------------------------------- |
| 🟢    | 中继活 + kimi 活 + WS 通                             | 全功能                                                |
| 🟡    | 中继活 + WS 通，**但 kimi 不活 / 不响应**（崩 / 卡） | 能看缓存历史；不能发新指令；**独有「重试拉起 kimi」** |
| ⚫    | 中继不可达（WS 断：电脑睡 / 断网 / 中继挂 / 隧道断） | 只能看本地最后缓存；什么都发不了                      |

> **校准**：合盖 / 电脑睡 = 中继死 = WS 断 = **⚫**，不是🟡。 专指"中继还活着、但底下 kimi acp 没了或卡了"，对应操作是中继自尝试把 kimi 重新拉起。

**将睡预警 + best-effort 保活** 🔴 *跨平台 API*

将睡是**预测**，叠加在🟢上的预警标记，**不直接改灯**。「尽量保活」= best-effort 开关：挡 idle 自动睡，**挡不住手动合盖**（硬件睡眠），边界写进 tooltip，不假装。保活 API 跨平台不同（macOS caffeinate / Windows SetThreadExecutionState），**Windows 优先验**。

**断线重连 + 快照对齐**

指数退避重连，重连中显示「重连中…」**不假装🟢**。连上后**不逐条重放**断线期 update，而是发**当前 state 快照**（每 sid 的流尾 / 待批准队列 / 状态点 / mode），端一次性对齐再接新 update。断线期超时拒绝的卡，快照里已是 S2b + 门铃补，**没有"错过批准却无痕迹"的黑洞**。

**诚实清单（验收表，不诚实即一票否决）**

| 真实情况           | UI 必须显示            | 反例                 |
| ------------------ | ---------------------- | -------------------- |
| 重连中             | 「重连中…」转圈        | 灯还🟢、输入框还能点  |
| kimi 崩（🟡）       | 🟡 + 「重试」           | 🟢假装能发            |
| 电脑睡 / 断网（⚫） | ⚫ + "最后同步于 xx:xx" | 显示旧流假装还活     |
| 保活挡不住合盖     | tooltip 写明           | 文案暗示"合盖也保活" |
| 断线期超时拒绝     | 快照 S2b + 门铃补      | 卡凭空消失无痕迹     |

## §13 遥控输入 · slash 命令

**输入框 + 中断**

- **输入永远发给 C 位 sid**：placeholder 带"发给：**会话名**"，切会话时跟着变——防串味在输入侧的最后一道闸。
- **「停」可见性随状态**：流式中亮且显眼（跑飞时 0.5 秒内要戳到），空闲时灰 / 隐藏（没在跑，停谁？摆亮的停按钮是误导）。显眼但不误导。

**快捷 chip：自用沉淀**

v1 内置"跑下测试 / commit 一下 / 解释刚干了啥 / 停换个方向"；可长按加自定义，存中继配置。点 chip = 填入并发送（一步）。**chip 是自用动机最直接的产物**——只有你自己用烦了，才知道该把哪几句变 chip。

**slash 命令菜单：精选 + 动态读**

输入 `/` 或点 `/` 按钮 → 命令菜单。命令**从 Kimi 的 `available_commands_update` 动态读**，不硬编码——Kimi 加新命令菜单自动有。

| 上手机（精选置顶带图标） | 为什么                             |
| ------------------------ | ---------------------------------- |
| `/skill`                 | 看 agent 现在有哪些能力（v1 只读） |
| `/status` · `/usage`     | 会话现状 / token 成本意识          |
| `/compact`               | 长会话上下文满了，远程压缩救命     |
| `/mcp` · `/tasks`        | MCP 连接状态 / 后台任务            |

非精选（custom-theme / import / sub-skill / update-config / write-goal / help）**折叠进"更多命令"**——既满足精选，又不丢"万一要用"。**桌面端 v2 = 全部命令展开**（含配置类命令，见 §14）。🔴 *slash 在 ACP 里怎么发*（发 `/xxx` 文本 or 专门调用，大概率前者，待验）。

**与 chip 的分工**：slash = Kimi 原生命令（动态读），chip = 你的自由文本常用语。都在输入区，不打架。

**插话语义** 🔴 *观察* **· 语音不画图标**

agent 忙时又发一句 Kimi 怎么处理，v0 没测；v1 输入框始终可发，不自动 cancel（太霸道），要明确打断用「停」再发。**语音 v3 才做，v1 不画🎤图标**——没有的功能别摆灰按钮骗点击（诚实）。

## §14 配置图形化 · 机器体检

> 两类配置、两种生效语义、可选项的权威来源是 Kimi。诚实承认 v1 只敢碰其中一半。

**机器体检：遥控 / 哨兵之外的第三件事**

点机器名打开的面板，定位是**远程体检表**——你不在场也能掌握"它现在健不健康、配了什么、有没有出问题"：连的哪个模型 / provider、key 有没有失效；MCP server 连没连上（connected / error）；当前哪些命令会被标红；加载了哪些 skills。**v1 只读 + key 脱敏**（防截屏 / 肩窥）。

**两类配置，分清**

|           | 会话级                        | 全局级                                            |
| --------- | ----------------------------- | ------------------------------------------------- |
| 是什么    | 这会话现在用什么 model / mode | provider / permission 默认 / hooks / MCP / skills |
| 怎么改    | 经 ACP set 🔴 *method 待验*    | v2 走 Kimi 原生命令                               |
| 改坏风险  | 低（Kimi 兜着）               | 高（但走原生命令后由 Kimi 保证格式）              |
| v1 图形化 | **可写**（切 model / mode）   | **只读**（机器体检）                              |

**会话头：model + mode 选择器**

每会话流顶一条细条：model 下拉 + mode 芯片。**provider 跟着 model 走**——model 名自带 provider 前缀（v0 实测 `myprovider/my-model`），选 model 即切 provider，**不独立切 provider**。mode 用图标 + 短文案表达哨兵在不在场（🛡手动 / 只读 / ⚡自动 / 🚀YOLO），必须一眼可见。下拉选项**从 configOptions 读**，不硬编码。

> **🔴 退路**：若 ACP set mode/model 不可用 → 退化为"新建会话时选、已建会话会话头只读可见当前值"。最差也只是"能看不能切"，透明性仍在。

**全局写操作：走 Kimi 原生命令，不要回滚安全网**

> **关键修正（封装不越界）**
> v2 增删 MCP / skill / 改配置，**优先走 Kimi 原生命令**（`mcp-config` / `update-config` / `sub-skill`），App 只提供友好入口触发，**不直接写文件**。格式正确性由 Kimi 保证，写坏风险低 → **"备份 + 校验 + 回滚"安全网从硬门槛降为"仅当不得不直接写文件时"的可选保险**。
> 这与 §13 桌面端"全部命令"是同一件事的两面：桌面端 v2 的配置管理 = 把这几个原生命令做好。设计简洁、复用原生、符合原则 7。

**配置能力分期分层**

| 操作                                | v1         | v1.5           | v2           |
| ----------------------------------- | ---------- | -------------- | ------------ |
| 切当前会话 model / mode             | ✅ 经 ACP 🔴 |                |              |
| 看全局配置（机器体检，只读 + 脱敏） | ✅          |                |              |
| 开关已配置的 MCP / skill            |            | 🔴 视热重载能力 |              |
| 增删 MCP / 装卸 skill / 改 rules    |            |                | ✅ 走原生命令 |
| 导入 / 导出配置                     |            |                | ✅            |

## §15 多端 UI 关系

> **逻辑层 100% 复用，UI 层"共享组件 + 按端适配布局"。** 选 Flutter 的核心价值在此；但"一套代码多端" ≠ "两端长得一模一样"。

**为什么不能 100% 同一套 UI**

手机端与桌面端在产品里**定位不同**：手机 = 不在场（遥控 + 哨兵，轻快专注，精选命令，只读体检）；桌面 = 在场（全功能工作台，全部命令，可触发配置原生命令，会话漂移）。强行一套 UI 直接搬，要么手机塞太多，要么桌面太简陋。两端是**同一产品的两个面**。

**复用清单**

| 100% 共享（同一 widget / 逻辑）                              | 按端适配（共享组件，布局 / 交互不同）    |
| ------------------------------------------------------------ | ---------------------------------------- |
| 活的流 StreamView、批准卡、工具卡、思考块、回复块、chip      | 整体布局：手机单列 / 桌面多列            |
| Riverpod 状态、会话 / 批准状态机、WS 通信、ACP 解析、风险判定 | 会话导航：手机顶栏横滑 / 桌面侧边栏      |
| 数据模型、配置读取、超时 / 倒计时逻辑                        | 命令菜单：手机精选 + 折叠 / 桌面全部     |
|                                                              | 配置：手机只读体检 / 桌面触发原生命令    |
|                                                              | 输入：手机软键盘 / 桌面物理键盘 + 快捷键 |

**布局对比（同一 StreamView，外围骨架按端）**

```
手机（单列·专注）              桌面（多列·全功能）
┌──────────────┐        ┌────────┬─────────────┬────────┐
│顶栏 灯·机器·标签·🔔│        │会话列表 │  活的流        │详情/体检│
│会话头 model·mode │        │(侧边栏) │ (同一组件)    │命令面板 │
│  活的流         │        │全部/搜索 ├─────────────┤会话信息 │
│  思考/回复/批准卡│        │        │ 输入(多行+全命令)│        │
│ chip · 输入·停·发 │        └────────┴─────────────┴────────┘
└──────────────┘
```

中间"活的流"两端用**同一个 StreamView**——会话漂移要求两端看同一条流，渲染必须一致；差异只在外围骨架。这正呼应原则 1：**状态一致，呈现按端**。

> 诚实提醒：Flutter 桌面端（尤其 Windows）成熟度低于移动端，窗口 / 托盘 / 全局快捷键等桌面特有能力可能要额外插件，v2 才碰，v1 专注手机正好避开。

## §A v0 实测证据摘要

> 关键 JSON 片段，给开发对照协议字段，省去重跑探针。

**session/new · configOptions（model/mode 可选项 + 当前值）**

```json
{ "sessionId": "session_caec4bfc-…",
  "configOptions": [
    { "id": "model", "currentValue": "myprovider/my-model",
      "options": [{ "value": "myprovider/my-model", "name": "My Model" }] },
    { "id": "mode", "currentValue": "default",
      "options": [
        {"value":"default","description":"Manual approvals; tools execute normally."},
        {"value":"plan","description":"Read-only planning; no tool execution."},
        {"value":"auto","description":"Fully autonomous — agent decides everything without asking."},
        {"value":"yolo","description":"Auto-approve tool actions, but the agent may still ask questions."}
      ] }
  ] }
```

**session/request_permission · 三选项 + reject 真阻断**

```jsonc
// agent → client：请求许可
{ "method": "session/request_permission",
  "params": { "sessionId": "…",
    "options": [
      {"optionId":"approve_once","kind":"allow_once"},
      {"optionId":"approve_always","kind":"allow_always"},
      {"optionId":"reject","kind":"reject_once"} ],
    "toolCall": { "title": "Bash", "…": "…" } } }
// client → agent：回 reject
{ "result": { "outcome": { "outcome": "selected", "optionId": "reject" } } }
// 随后 tool_call_update.status = "failed"，命令未执行 ✓
```

**session/update · 流式分类（按 sessionId 路由）**

```jsonc
// 思考（可折叠）  { "sessionUpdate": "agent_thought_chunk", "content": {"type":"text","text":"…"} }
// 回复（主体）    { "sessionUpdate": "agent_message_chunk", "…" }
// 工具调用       { "sessionUpdate": "tool_call", "status": "pending", "…" }
// 工具流式/结果  { "sessionUpdate": "tool_call_update", "status": "in_progress|completed|failed", "…" }
// slash 命令列表 { "sessionUpdate": "available_commands_update", "availableCommands": [ "…" ] }
```

## §B 术语表

| 术语     | 含义                                                    |
| -------- | ------------------------------------------------------- |
| 遥控     | 人主动向 agent 下达意图                                 |
| 哨兵     | agent 在需要人时主动通知人                              |
| 机器体检 | 远程只读掌握机器配置与健康                              |
| 会话漂移 | 同一条活会话在不同设备间无缝接续，状态不分裂            |
| 单一真相 | 所有设备共享同一份会话状态，设备只是视图                |
| 中继     | 跑在 agent 机器上、连接 agent 与各端的中间层（Go 常驻） |
| 许可裁决 | 中继作为 ACP client，按会话策略应答 permission          |
| 门铃     | 系统级推送（v1 = Bark，v2 = APNs），只叫醒不传内容      |
| C 位     | 主屏当前选中显示的会话                                  |
